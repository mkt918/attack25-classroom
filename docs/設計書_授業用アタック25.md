# 授業用アタック25 設計書(改訂版)

初版の設計書(ネット対戦サービス想定)を、実際の利用目的に合わせて全面改訂したもの。

---

## 1. 目的と前提

- **利用シーン**: 授業内で数十人の生徒を数班(1班2〜6人)に分け、班ごとに同時並行でアタック25型クイズを実施する
- **問題内容**: 授業の用語・知識問題。先生が自分で追加する
- **プレイ形式**: **生徒一人1台のPC**で参加する(決定事項)
- **進行**: 司会・操作係は置かず、**プログラムが全自動で進行**する(決定事項)
- **ホスティング**: GitHub Pages(静的SPA)
- **同期基盤**: Firebase(最小構成)

### 初版から削ったものと理由

| 削ったもの | 理由 |
|---|---|
| Firestore | 審判ロジックを先生のブラウザに一元化したため不要に(後述) |
| ホスト切断→ホスト移譲 | ホストは常に先生のPC。落ちたら開き直せば済む(状態はDBに残る) |
| App Check・本格的な不正対策 | 相手は教室の生徒。正解データを配信しない構造(後述)で実用上十分 |
| 問題集の公開/共有機能・CSVバージョン管理 | 先生が自分の問題を使うだけ |
| 早押しの厳密な公平性検討 | 校内LANは遅延が揃っており、トランザクション先着で十分 |

### 初版から残すもの

- パネル反転ロジックの**純粋関数化+ユニットテスト**(ゲームの核)
- **メタ定義駆動**のルール設定UI(トグル/スライダー自動生成)。プリセット2〜3個
- GitHub Pages + **ハッシュルーティング**(`/#/room/xxx`)
- RTDB トランザクションによる早押し先着確定
- サーバー時刻オフセット(`.info/serverTimeOffset`)によるタイマー同期

## 2. 全体アーキテクチャ

```
[GitHub Pages(静的SPA・単一コードベース)]
        │
        ├── 先生ダッシュボード(1タブ)────────┐
        │     ・問題の投入/管理                │ 審判ロジック(状態機械)は
        │     ・部屋の一括作成                  │ 先生のブラウザだけで実行
        │     ・全部屋モニタ/介入              │
        │                                      ▼
        └── 生徒画面(人数分) ◄──► [Firebase RTDB + 匿名認証]
              ・部屋コードで入室                 揮発的なゲーム状態のみ保持
              ・早押し/解答/パネル選択
```

### 2-1. 審判は「先生のPC」に一元化(最重要判断)

- 先生のブラウザ1タブが**全部屋の状態機械を一括駆動**する。4〜6人×数班程度の判定処理は軽く、1タブで十分捌ける
- 生徒クライアントは「入力(早押し・解答・パネル選択)を書き込み、状態を購読して表示するだけ」の状態表示器に徹する
- 先生は自動進行に**いつでも介入できる**: 一時停止・問題スキップ・判定の取り消し(Undo)・全部屋一覧モニタ。「自動だが先生が神」の構造
- 弱点: 先生のPCが落ちると全体停止。教室ではタブを開き直せば復旧するので許容(状態はRTDBに残る)

### 2-2. DB は RTDB 1本(Firestore 廃止)

- 問題は先生がダッシュボードに**スプレッドシートからコピペ(TSV貼り付け)**で投入。保存は localStorage + JSONファイルのエクスポート/インポート
- 出題時は**問題文と選択肢だけ**を RTDB に流す。**正解データは先生のブラウザから外に出さない** — 生徒側に正解が一切届かないため、開発者ツールを開いてもカンニング不能(教室対戦では生徒が本気で突いてくる前提で設計する)
- Firebase 構成は「RTDB + 匿名認証」の最小2点のみ

### 2-3. 問題形式は4択を基本とする

- 全自動進行には機械的に正誤が決まる形式が必須。用語クイズとの相性も良い(正解の用語+ダミー3つ)
- 記述式は表記ゆらぎの誤判定で教室が荒れるリスクがあるため、v1では見送り(将来拡張点として型だけ確保)

## 3. データ構造

### 3-1. RTDB(ゲーム進行・揮発)

```
sessions/{sessionId}/               … 1授業=1セッション
  meta: { teacherUid, createdAt }
  rooms/{roomId}/
    meta:    { phase, questionIndex, phaseDeadline }   ← 先生のみ書込可
    players/{uid}: { name, color, seat, connected, correctCount, attackStock }
    board:   { "0": null|uid, …, "24": … }             ← 先生のみ書込可
    question:{ text, choices[4] }                      ← 正解indexは含めない
    buzz/
      open:  true|false
      first: { uid, at: ServerTimestamp }              ← トランザクション先着1名
    answer:  { uid, choiceIndex, at }
    judgeLog/{seq}: { event, payload, at }             ← 監査ログ兼Undo素材
    presence/{uid}: { lastSeen }                       ← onDisconnect で自動更新
```

セキュリティルールは一方向データフローをそのまま写像する:

- `buzz/first`・`answer`・パネル選択: 本人(auth.uid)のみ書込可
- `meta`・`board`・`players/*/correctCount`: 先生のuidのみ書込可
- 正解データ: **そもそもRTDBに存在しない**(先生のブラウザ内メモリのみ)

### 3-2. 先生ローカル(localStorage + ファイル)

```
questionSets: [
  { title, questions: [ { text, choices[4], answerIndex, note } ] }
]
ruleConfig(前回設計のスキーマを縮小・version付き):
  { version, flipMode(othello|none), attackChance{enabled, requiredCorrect},
    answerTimeoutSec, perQuestionSec, totalCount, victory }
```

- TSV貼り付けの列定義: `問題文 / 選択肢1 / 選択肢2 / 選択肢3 / 選択肢4 / 正解番号`(選択肢1を常に正解にして自動シャッフルする案も可。作問が楽になるため推奨)

## 4. 処理の流れ

### 4-1. 授業開始フロー

1. 先生がダッシュボードを開く → 問題セットを選ぶ → 班の数を指定 → 部屋を一括作成
2. 画面に部屋コード一覧が出る(「1班: ABC1」等)。板書やプロジェクターで生徒に伝える
3. 生徒は URL を開き、部屋コード+名前を入力して入室(匿名認証・登録なし)
4. 全部屋の人数が揃ったのを先生がモニタで確認 → 「全部屋一斉スタート」

### 4-2. ゲームループ(部屋ごと・全自動)

```
Q_READING(問題表示) → BUZZ_OPEN(早押し受付)
  ├─ 先着あり → ANSWERING(4択・制限時間付き)
  │     ├─ 正解 → PANEL_SELECT → FLIP_RESOLVE(オセロ反転) → 次問 or 終了判定
  │     └─ 誤答/時間切れ → ペナルティ適用 → 残者で BUZZ_OPEN 再開 or 次問
  └─ 誰も押さず時間切れ → 次問
終了条件成立 → RESULT(順位表示) → 先生が結果を回収
```

- 全 phase は `meta.phase` + `meta.phaseDeadline`(サーバー時刻基準)で表現。各端末はサーバー時刻オフセットで補正した残り時間を描画する
- 早押し: 各自のPCでボタンまたはスペースキー。RTDBトランザクションで先着1名のみが `buzz/first` を取得
- パネル反転: `resolveFlip(board, placedIndex, uid, config) → newBoard` の純粋関数。UI・DB非依存でユニットテスト対象

### 4-3. 復席処理(必須機能)

- 授業中はPCスリープ・誤リロードが頻発する前提で設計する
- 匿名認証のuidは端末に永続するため、再アクセス時に `players/{uid}` が存在すれば**自動で元の席・パネル・得点のまま復帰**
- 切断中は早押し対象から除外(`connected=false`)。パネルは保持

---

## 5. ルール設定UI(先生向け)

- 設定スキーマのメタ定義(型・範囲・デフォルト・説明文)から UI を自動生成: bool→トグル、数値範囲→スライダー、列挙→セグメントボタン
- プリセット: 「本家風」「短時間(10問)」+カスタム
- 設定はゲーム開始時にスナップショットされ、進行中は変更不可(挙動が途中で変わる事故防止)

## 6. リスクと事前確認事項

| # | リスク | 対応 |
|---|---|---|
| 1 | **学校ネットワークのフィルタリングで Firebase が塞がれている** | **最大の実行リスク。開発着手前に**教室のネットワークから疎通確認ページを開いて確認する。塞がれていたら設計ごと変更が必要(校内サーバー等) |
| 2 | RTDB 無料枠は同時接続100まで | 数十人+先生なら収まる。複数クラス同時実施をする場合は要注意 |
| 3 | 生徒による正解の覗き見 | 正解を配信しない構造で対処済み(§2-2) |
| 4 | 誤判定・誤操作 | judgeLog による Undo と先生の介入ボタンで対処 |
| 5 | ブラウザ差(学校PCの古い環境) | 対象ブラウザを事前確認。特殊APIは使わない構成なので基本は問題なし |

## 7. やり直しコストが高い判断(この段階で確定)

1. **審判の先生PC一元化**(§2-1) — データフロー・ルール・障害設計の土台
2. **正解データを配信しない構造**(§2-2) — 後から分離するのは全面改修
3. **RTDB のパス設計と一方向データフロー**(§3-1) — セキュリティルールと全購読コードが載る
4. **ruleConfig スキーマ(version付き)**(§3-2) — UI自動生成・保存データとの三者契約
5. **TSV列定義**(§3-2) — 先生の手元資産(問題スプレッドシート)の形式になるため実質変更不可
6. **ハッシュルーティング** — 共有URLの形式

UIデザイン・効果音・演出・プリセット内容は後からいくらでも変えられる。

---

## 8. 実装の段階分け

1. **M0: Firebase 疎通確認** — 学校ネットワークで RTDB に読み書きできるかだけ確認する1ページ。**何よりも先にやる**
2. **M1: ルールエンジン** — 反転・勝敗判定の純粋関数+ユニットテスト(DB・UI無し)
3. **M2: 最小対戦ループ** — 1部屋・固定ルール・固定問題で「早押し→4択→パネル→反転」が回る
4. **M3: 先生ダッシュボード** — 問題TSV投入・部屋一括作成・モニタ・介入(Undo/スキップ/一時停止)
5. **M4: 教室運用機能** — 復席処理・ルール設定UI・結果表示・効果音
6. **M5: 磨き込み** — 演出、プロジェクター用の結果発表画面など

M0 が失敗したら以降の設計を見直すため、必ず最初に実施する。
